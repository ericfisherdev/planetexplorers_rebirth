# Phase 1: Unity 6+ Migration - Research

**Researched:** 2026-03-28
**Domain:** Unity engine migration (5.2.4f1 to 6000.3.x LTS)
**Confidence:** HIGH

## Summary

Migrating this project from Unity 5.2.4f1 to Unity 6 (6000.3.x LTS) is a significant but well-understood task. The codebase has ~2,888 C# scripts, 10 UnityScript (.js) files, and 197 shaders. The major API changes fall into a finite set of categories: deprecated component accessors (.rigidbody, .collider, .renderer, .camera, .light), removed scene management APIs (Application.LoadLevel), removed UnityScript support, removed legacy particle system classes (ParticleEmitter/ParticleAnimator/ParticleRenderer), and the .NET runtime upgrade from 3.5 to modern .NET.

Unity's API Updater will automatically handle many of the deprecated-to-modern API conversions (component accessors marked `[UnityUpgradable]`), but it cannot handle everything -- particularly removed APIs, UnityScript files, and legacy particle system classes. The project also has 6 files with native P/Invoke (`DllImport`) calls that need platform review, and all ProjectSettings .asset files will need regeneration by the new editor.

**Primary recommendation:** Open the project directly in Unity 6000.3 LTS (skipping intermediate versions), let the API Updater run, then systematically fix remaining compilation errors in priority order. The "sequential upgrade through every LTS" approach is impractical for a project that does not compile in its original version (missing plugins). A direct jump to Unity 6 with manual fixups is the correct strategy.

## Architecture Patterns

### Recommended Migration Structure

```
ProjectSettings/          # Will be regenerated by Unity 6 on first open
Assets/
  Scripts/               # ~2,888 .cs files -- API migration target
  Resources/Particle/    # 10 .js files -- must convert to C# or delete
  *.shader               # 197 shaders -- review for ShaderLab compatibility
```

### Pattern 1: Batch Pre-Processing Before Editor Open

**What:** Use sed/grep to fix the highest-volume deprecated patterns BEFORE opening in Unity 6 editor, so the API Updater has less work and the compile error count is manageable.
**When to use:** For well-defined, mechanical replacements with zero ambiguity.
**Example:**
```bash
# Replace Application.LoadLevel("x") with SceneManager.LoadScene("x")
# Add 'using UnityEngine.SceneManagement;' to affected files
# Replace Application.loadedLevelName with SceneManager.GetActiveScene().name
```

### Pattern 2: Let API Updater Handle Upgradable APIs

**What:** Unity's built-in API Updater automatically rewrites code for APIs marked `[UnityUpgradable]`. Component accessors (.rigidbody, .collider, .renderer, .camera, .light) are in this category.
**When to use:** After opening the project in Unity 6 editor.
**Why:** The updater understands context, handles edge cases, and produces correct GetComponent<T>() calls.

### Pattern 3: Delete-and-Replace for Unsupported Code

**What:** UnityScript (.js) files and legacy particle system classes cannot be auto-updated. Delete the .js files and rewrite as C# (they are small particle utility scripts). Replace ParticleEmitter/ParticleAnimator/ParticleRenderer references with ParticleSystem equivalents.
**When to use:** For APIs that were fully removed (not just deprecated) between Unity 5 and Unity 6.

### Pattern 4: ProjectSettings Regeneration

**What:** Delete all binary .asset files in ProjectSettings/ (except ProjectVersion.txt), then open in Unity 6 to regenerate them with correct defaults.
**When to use:** Binary settings files from Unity 5.2.4f1 are not forward-compatible. Unity 6 will either fail to parse them or silently use wrong settings.
**Details:** The following files will be regenerated:
- AudioManager.asset
- DynamicsManager.asset (physics settings)
- GraphicsSettings.asset
- InputManager.asset
- NavMeshAreas.asset / NavMeshLayers.asset
- Physics2DSettings.asset
- ProjectSettings.asset (player settings, company name, etc.)
- QualitySettings.asset
- TagManager.asset
- TimeManager.asset

### Anti-Patterns to Avoid

- **Sequential LTS upgrade through 7 versions:** Impractical waste of time for a project that doesn't compile at any version. Jump directly.
- **Migrating to URP:** The codebase has 197 shaders targeting built-in render pipeline. URP migration is a separate, massive project. Stay on built-in.
- **Ignoring UnityScript files:** Unity 6 will hard-fail on .js files. They must be dealt with before the project can open.
- **Trying to preserve exact ProjectSettings:** Binary settings from 5.2 are garbage in Unity 6. Let them regenerate from defaults.

## Shaders

**197 shader files** in the project, all using Unity 5.x ShaderLab syntax targeting the built-in render pipeline.

**Unity 6 compatibility for built-in pipeline shaders:** Built-in render pipeline is still fully supported in Unity 6. Most ShaderLab syntax from Unity 5.x compiles in Unity 6 without changes. Known issues:

1. **`Cull` / `ZWrite` / `ZTest` defaults unchanged** -- should work
2. **Surface shader syntax** -- still supported in built-in pipeline
3. **CG to HLSL:** Unity 6 uses HLSL internally but still accepts `CGPROGRAM`/`ENDCG` blocks in built-in pipeline. No migration needed for Phase 1.
4. **Potential warnings:** Some shader features may produce deprecation warnings but still compile

**Recommendation:** Do not modify shaders in Phase 1. Open the project, let Unity recompile shaders, and fix only hard errors (if any). Shader warnings are acceptable.

**Confidence:** MEDIUM -- shader compatibility between 5.x and 6.x built-in pipeline is generally good, but edge cases exist in custom surface shaders and legacy fixed-function syntax.

## Common Pitfalls

### Pitfall 1: Attempting Sequential LTS Upgrades

**What goes wrong:** Following Unity's official recommendation to upgrade through every intermediate LTS (5.x -> 2017 -> 2018 -> 2019 -> 2020 -> 2021 -> 2022 -> 6.0) -- 7 upgrade steps.
**Why it happens:** Unity docs explicitly recommend this.
**How to avoid:** This recommendation is for projects that compile and run at their current version. This project does NOT compile at Unity 5.2.4f1 (missing plugins). There is no benefit to upgrading through intermediates when the project cannot be tested at any step. Jump directly to Unity 6.
**Warning signs:** You are downloading 7 different Unity editor versions.

### Pitfall 2: Collider False Positives in API Migration

**What goes wrong:** The `.collider` accessor grep catches both deprecated `gameObject.collider` (Component accessor shortcut) and valid `raycastHit.collider` (RaycastHit property, NOT deprecated).
**Why it happens:** Both patterns match `.collider` regex.
**How to avoid:** Let the Unity API Updater handle component accessor changes. It understands the type context and only converts actual deprecated usages. Do NOT use blind find-and-replace for `.collider`.
**Warning signs:** Runtime errors where `GetComponent<Collider>()` returns null on a RaycastHit.

### Pitfall 3: ProjectSettings Binary Corruption

**What goes wrong:** Opening the project in Unity 6 with Unity 5.2 binary ProjectSettings .asset files causes import errors, silent setting corruption, or editor crashes.
**Why it happens:** Binary serialization format changed across major Unity versions.
**How to avoid:** Back up the originals (for reference), then delete all .asset files in ProjectSettings/ before opening in Unity 6. Keep ProjectVersion.txt.
**Warning signs:** Editor hangs on "Importing Assets" or shows cryptic YAML parse errors.

### Pitfall 4: Forgetting SceneManagement Using Directive

**What goes wrong:** Replacing `Application.LoadLevel` with `SceneManager.LoadScene` but forgetting to add `using UnityEngine.SceneManagement;` at the top of the file.
**Why it happens:** `Application` is in `UnityEngine` which is already imported. `SceneManager` is in a sub-namespace.
**How to avoid:** Script the replacement to always add the using directive. Check if it already exists before adding.
**Warning signs:** CS0103 "The name 'SceneManager' does not exist in the current context."

### Pitfall 5: UnityScript Files Blocking Project Import

**What goes wrong:** Unity 6 cannot parse .js files at all and refuses to import the project.
**Why it happens:** UnityScript compiler was completely removed in Unity 2018.2.
**How to avoid:** Delete or rename all 10 .js files BEFORE opening the project in Unity 6. Convert the ones that are needed (SqliteAccess.js has a C# counterpart, particle scripts can be rewritten trivially).
**Warning signs:** Import errors mentioning ".js" files immediately on project open.

### Pitfall 6: Expecting Clean Compilation After Phase 1

**What goes wrong:** Expecting zero compile errors after Unity migration. The project will still have hundreds of errors from missing proprietary plugins (NGUI 417 files, uLink, FMOD, etc.).
**Why it happens:** Confusing "project opens in editor" with "project compiles."
**How to avoid:** Phase 1 success criteria is "project opens in Unity 6+ editor without import-blocking errors" -- NOT clean compilation. Missing plugin errors are expected and acceptable. Phase 2 (stubs) and Phase 3 (clean compilation) handle those.
**Warning signs:** Spending time trying to fix NGUI/uLink/FMOD errors during Phase 1.

## Code Examples

### Scene Management Replacement
```csharp
// BEFORE (Unity 5.x):
Application.LoadLevel("MainMenu");
Application.LoadLevel(2);
string name = Application.loadedLevelName;
bool loading = Application.isLoadingLevel;

// AFTER (Unity 6):
using UnityEngine.SceneManagement;
// ...
SceneManager.LoadScene("MainMenu");
SceneManager.LoadScene(2);
string name = SceneManager.GetActiveScene().name;
// isLoadingLevel has no direct equivalent; use async load operation
```

### UnityScript to C# Conversion Example
```csharp
// BEFORE (Wind.js - UnityScript):
// #pragma strict
// function Update() { transform.Rotate(...); }

// AFTER (Wind.cs - C#):
using UnityEngine;
public class Wind : MonoBehaviour
{
    void Update()
    {
        transform.Rotate(/* ... */);
    }
}
```

### Legacy Particle System Replacement
```csharp
// BEFORE (Unity 5.x):
ParticleEmitter emitter = GetComponent<ParticleEmitter>();
emitter.emit = true;

// AFTER (Unity 6):
ParticleSystem ps = GetComponent<ParticleSystem>();
ps.Play();
```

### FindObjectsOfType Replacement (Unity 6 specific)
```csharp
// BEFORE:
var objects = FindObjectsOfType<MyType>();

// AFTER (Unity 6):
var objects = FindObjectsByType<MyType>(FindObjectsSortMode.None);
// Or if you need a single object:
var obj = FindFirstObjectByType<MyType>();
```

## Open Questions

1. **Shader edge cases in built-in pipeline**
   - What we know: ShaderLab syntax is broadly compatible. Built-in pipeline is supported.
   - What's unclear: Whether any of the 197 shaders use fixed-function syntax that was fully removed
   - Recommendation: Open project, let Unity recompile shaders, fix only hard errors

2. **EditorBuildSettings.asset scene list**
   - What we know: This file contains the list of scenes to include in builds
   - What's unclear: Whether the scene references survive ProjectSettings deletion
   - Recommendation: Note the scene list from the original file before deleting, manually re-add scenes in Unity 6 Build Settings

3. **Scale of API Updater effectiveness on a direct 5.x -> 6.x jump**
   - What we know: API Updater handles `[UnityUpgradable]` marked APIs. Component accessors are in this category.
   - What's unclear: Whether the updater's database covers the full 5.x -> 6.x delta or only recent-version deltas
   - Recommendation: Run API Updater first, then manually fix remaining errors. Batch pre-process the most predictable changes (LoadLevel, UnityScript) before opening.
